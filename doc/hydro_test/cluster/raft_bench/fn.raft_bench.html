Benchmarks raft_server with closed-loop bench_clients.

Clients send each request to the leader that a majority of replicas name in their latest leader views, holding requests while there is none. Every member’s election timer fires at startup, so a member can win an early term that the others skip, and a leader can be deposed while some replicas still name it. Requests sent to such a leader are lost, and bench_client never retries, so their virtual clients stall for the rest of the run. Clients therefore use a leader only while a majority’s latest views name it, which rules out both; requests already in flight to a leader when it is deposed are still lost.

A request completes when the first replica commits it, which is the leader, since followers learn the commit index from a later AppendEntries. A replica that receives a request while not leading forwards it to its leader hint, and drops it when it has none.

  • election_timeout_millis: member i uses election_timeout_millis + 130 * i, so that members’ election timers do not stay aligned.
  • heartbeat_interval_millis: the leader only sends AppendEntries on a heartbeat, so this interval bounds commit latency from below.
