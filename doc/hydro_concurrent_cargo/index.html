Shared locking and job directory utilities for parallel cargo builds in Hydro.

This crate provides the coordination primitives for running multiple cargo builds concurrently against a shared target directory using per-job symlinked directories.

§Why

Hydro compiles each generated program (one per deployed process, sim test, …) as an example of a generated trybuild project. Cargo allows a single build per target directory (it takes an exclusive lock on it), so compiling those programs concurrently through cargo directly would serialize them. At the same time they all share the same, expensive dependency graph, so giving each its own target directory would recompile everything per program.

§The trick: prebuild once, then share the artifacts without cargo’s lock

Builds run in two phases, coordinated by this crate’s own locks:

  1. Prebuild (exclusive .prebuild.lock): one cargo build compiles every dependency — including the trybuild dylib that the generated programs link against — into the shared target dir. While it runs, no final build is in flight, so it may freely write shared state.
  2. Final builds (shared .prebuild.lock): many cargo builds run concurrently, each with its own target-dir root under jobs/<JOB>/, so cargo’s locks are per job and never contend. The shared, prebuilt state is made visible inside each job dir via symlinks. This is safe without cargo’s lock only because of an invariant the two phases establish: a final build reads shared state but never writes it — everything it reads is fresh (the prebuild just built it, with identical features/rustflags, so cargo finds the fingerprints up to date), and everything it creates (its own example unit, its uplifted artifacts) has a job-unique path. Switching configuration (features, rustflags, toolchain) takes the lock exclusive again, draining all in-flight final builds before the prebuild rewrites shared state.

Unrelated cargo processes building in the shared target dir (a developer’s cargo build, an IDE) are kept out the same way cargo keeps itself out: this crate holds the shared target dir’s own .cargo-build-lock shared for the whole prebuild + final build, and cargo takes that file exclusive for any build there, so the two mutually exclude (“Blocking waiting for file lock on build directory”). This is also why every cargo spawned by this crate — prebuild included — gets a jobs/* root rather than the shared dir: a child cargo using the shared dir would wait forever on the lock its own parent holds.

§Configurations and the __CARGO_DEFAULT_LIB_METADATA optimization

A configuration is a (crate, features, rustflags, compiler) tuple. Cargo hashes all of these into the filenames of rlibs, so artifacts of different configurations coexist in the shared deps/ and are cached side by side — with one exception: the filename of a path package’s dylib carries no hash (libX_dylib.so), so every configuration would want to write the same file. The trybuild dylib is thus the single shared resource configurations fight over, and the design has two modes (see run_prebuild, dylib_lib_name):

  • Default: the fingerprint of rustflags + compiler version (toolchain_fingerprint) is baked into the dylib’s [lib] name, so different toolchains/rustflags get distinct files. Features are not part of the name, so switching features replaces the dylib: there is a single .prebuild.lock, every build holds it shared through its final build, and a configuration switch takes it exclusive — draining all in-flight builds before the prebuild renames the manifest and rebuilds. Concurrency is therefore limited to builds of one configuration at a time: while test binary A (features {sim}) has final builds in flight, test binary B (features {sim, deploy}) blocks until they finish, then rebuilds the dylib, then A blocks on B — alternating binaries ping-pong the shared dylib.
  • __CARGO_DEFAULT_LIB_METADATA=1 (set in CI): this undocumented cargo variable (used by rust-lang/rust’s bootstrap) makes cargo hash dylib filenames too (libX_dylib-<hash>.so), so every configuration’s dylib is a distinct file and the manifest never changes. Shared state becomes append-only across configurations — nothing one configuration writes is ever read by another — so the lock can be split per configuration: one .prebuild-<key>.lock each, with the cross-configuration .global-prebuild.lock taken only around a prebuild’s actual cargo build so two prebuilds never write deps/ at the same time. The concurrency this unlocks: final builds of different configurations run simultaneously, and a prebuild for one configuration runs while another configuration’s final builds are in flight. For nextest, which runs many test binaries with differing feature sets at once, that is the difference between the binaries serializing on each other and all of them proceeding in parallel — and every configuration’s dylib stays cached instead of being rebuilt on each switch.

Why a prebuild for configuration B may overlap configuration A’s final builds: cargo only writes a unit’s files when the unit is dirty (fresh units are not touched at all; the legacy-layout build-script-build re-link rewrites only the job-local uplift). B’s prebuild therefore writes B-specific units, which have B’s hashes and are never read by A, plus any unit shared with A that is dirty. A’s final builds read only units A’s own prebuild completed, so a shared unit is fresh for B — unless its inputs changed since A’s prebuild. That is the precondition: all concurrent builds must come from one source state. Within a test run it holds (test binaries are built before any runs, and the prebuild stamp is keyed on the binary’s mtime); running test processes from two different source states at once is unsupported in either mode (in default mode A’s --frozen final builds would panic with “unexpected recompilation”). The prebuild-vs-prebuild case is different — two configurations can both be dirty on the same not-yet-built shared unit — which is exactly what .global-prebuild.lock serializes.

Mixing builds with and without the variable against one target dir is unsupported: they would rename the shared manifest under different locks. Because the hashed dylib name is what the final artifacts link against (DT_NEEDED), loader search paths must include wherever that hashed file lives; see dylib_search_dirs.

§Layouts

Cargo’s new build-dir layout (-Zbuild-dir-new-layout, default on current nightly) moves everything under build/<pkg>/<unit-hash>/; see BuildDirLayout (detected at compile time by build.rs). The same job-dir structure works for both layouts: the job’s build/ is a real directory two levels deep whose children are symlinks, so writes cargo makes at that level (legacy: re-linking build-script-build; new: the job’s own example unit, which for the simulator is the same cargo unit in every job) stay job-local.

libX_dylib is the shared trybuild dylib (the user crate + hydro_lang built once by the prebuild) that every final artifact links against; libsim_dylib is a final per-job artifact (the simulator’s cdylib) that links against it.

Loader search paths (rpath / LD_LIBRARY_PATH) for libX_dylib are computed by dylib_search_dirs and only ever name state that outlives the build: the job’s debug/ and the shared location (deps/ on legacy, the shared unit out/ dirs on new) — never jobs/<JOB>/debug/build/, which is repopulated on every build (and job dirs are shared by tests whose generated programs are identical).
