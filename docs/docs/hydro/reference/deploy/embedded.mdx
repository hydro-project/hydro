# Embedded Mode

Hydro's standard deployment model compiles each location into a standalone binary and manages networking automatically. But sometimes you need more control — maybe you're integrating Hydro into an existing Rust application, or you need to wire up custom I/O like DPDK, a game engine's event loop, or a hardware interface. Embedded mode is designed for these cases.

Instead of producing self-contained binaries, embedded mode generates a Rust source file containing one plain function per location. Each function returns a [`Dfir`](rust:dfir_rs::scheduled::context::Dfir) dataflow graph that you drive manually. You decide when to tick it, how to feed it data, and where the outputs go.

## When to Use Embedded Mode
- **Incremental adoption**: You have an existing Rust codebase and want to introduce Hydro for a specific computation without restructuring your application around Hydro Deploy.
- **Custom I/O**: You need to connect Hydro to a transport or runtime that Hydro Deploy doesn't support (DPDK, shared memory, a game loop, etc.).
- **Library use**: You want to ship a crate that uses Hydro internally but exposes a normal Rust API to consumers.

When your Hydro program sends data between processes, the generated functions gain additional `network_out` and `network_in` parameters. You wire these up yourself — for example with in-memory channels, Unix sockets, or any transport you like. See [Networking](#networking) below for details.

## How It Works
Embedded mode uses a `build.rs` script to compile your Hydro program at build time. The generated code is then `include!`-ed into your crate. The workflow has three parts:

1. **Define your Hydro logic** using [`Location::embedded_input`](rust:hydro_lang::location::Location::embedded_input) and [`Stream::embedded_output`](rust:hydro_lang::live_collections::Stream::embedded_output) to mark where data enters and leaves the dataflow.
2. **Generate code** in `build.rs` using [`generate_embedded`](rust:hydro_lang::compile::deploy::DeployFlow::generate_embedded).
3. **Call the generated function** from your application, passing in streams and output callbacks.

Let's walk through a complete example that capitalizes strings using Hydro in embedded mode.

### 1. Define the Hydro Logic
Write your Hydro function as usual, but use `embedded_input` to create an input stream and `embedded_output` to mark where results should be emitted:

```rust title="my_hydro_crate/src/lib.rs"
use hydro_lang::prelude::*;

pub fn capitalize<'a>(input: Stream<String, Process<'a, ()>>) {
    input
        .map(q!(|s| s.to_uppercase()))
        .embedded_output("output");
}
```

[`embedded_input`](rust:hydro_lang::location::Location::embedded_input) creates a field on a generated `EmbeddedInputs` struct — the name you pass (`"input"`) becomes the field name. Its element type, boundedness, ordering, and retries (`embedded_input::<T, B, O, R>`) are usually inferred from where the stream is used, here `capitalize`'s parameter; they are what the dataflow assumes of the stream, and so what the host must promise (see [Promising Guarantees](#promising-guarantees)). Similarly, [`embedded_output`](rust:hydro_lang::live_collections::Stream::embedded_output) creates a field on a generated `EmbeddedOutputs` struct — the name (`"output"`) becomes the field name. The output field accepts an `impl FnMut(T)` closure, wrapped in an [`OutputChannel`](rust:hydro_lang::compile::embedded_runtime::OutputChannel), that will be called for each emitted element.

Your base crate also needs to declare an empty `stageleft_macro_entrypoint` feature. This is required by the Stageleft code generation machinery to set up the correct re-exports:

```toml title="my_hydro_crate/Cargo.toml"
[features]
stageleft_macro_entrypoint = []
```

### 2. Generate Code in `build.rs`
Create a wrapper crate that depends on your Hydro crate.

Your wrapper crate needs the following dependencies:

```toml title="my_wrapper_crate/Cargo.toml"
[dependencies]
hydro_lang = { version = "...", features = ["runtime_support"] }
my_hydro_crate = { path = "../my_hydro_crate", features = ["stageleft_macro_entrypoint"] }

[build-dependencies]
hydro_lang = { version = "...", features = ["build"] }
my_hydro_crate = { path = "../my_hydro_crate" }
prettyplease = { version = "0.2.0", features = ["verbatim"] }

[dev-dependencies]
dfir_rs = { version = "..." }
tokio = { version = "1", features = ["full"] }
```

The `runtime_support` feature is needed at runtime to provide the DFIR runtime. The `build` feature is needed in `build-dependencies` for the code generation APIs.

In its `build.rs`, construct a [`FlowBuilder`](rust:hydro_lang::compile::builder::FlowBuilder), wire up the logic, and call [`generate_embedded`](rust:hydro_lang::compile::deploy::DeployFlow::generate_embedded):

```rust title="my_wrapper_crate/build.rs"
use hydro_lang::location::Location;

fn main() {
    println!("cargo::rerun-if-changed=build.rs");

    let mut flow = hydro_lang::compile::builder::FlowBuilder::new();
    let process = flow.process::<()>();

    // Wire up the Hydro logic with an embedded input.
    my_hydro_crate::capitalize(process.embedded_input("input"));

    // Compile and generate the embedded code.
    let code = flow
        .with_process(&process, "capitalize")
        .generate_embedded("my_hydro_crate");

    let out_dir = std::env::var("OUT_DIR").unwrap();
    std::fs::write(
        format!("{out_dir}/embedded.rs"),
        prettyplease::unparse(&code),
    )
    .unwrap();
}
```

The string `"capitalize"` passed to [`with_process`](rust:hydro_lang::compile::builder::FlowBuilder::with_process) becomes the name of the generated function. The argument to `generate_embedded` is the name of the crate containing your Hydro logic (hyphens are automatically replaced with underscores).

### 3. Include and Use the Generated Code
In your wrapper crate's `lib.rs`, include the generated file:

```rust title="my_wrapper_crate/src/lib.rs"
#[allow(unused_imports, missing_docs)]
pub mod embedded {
    include!(concat!(env!("OUT_DIR"), "/embedded.rs"));
}
```

Now you can call the generated function from anywhere in your application:

```rust,ignore
use dfir_rs::futures;

async fn run() {
    // Create an input stream from any source you like.
    let input = futures::stream::iter(vec![
        "hello".to_owned(),
        "world".to_owned(),
    ]);

    // Collect outputs via a closure.
    let mut results = vec![];
    let mut outputs = embedded::capitalize::EmbeddedOutputs {
        output: OutputChannel::new(|s: String| {
            results.push(s);
        }),
    };

    // Build and run the dataflow.
    // Every input states what the host promises about its stream (see Promising Guarantees).
    let inputs = embedded::capitalize::EmbeddedInputs {
        input: InputChannel::new(
            input,
            Promises::new()
                .total_order(manual_proof!(/** the list's order is the order to process */))
                .exactly_once(manual_proof!(/** each element appears once in the list */)),
        ),
    };
    let mut flow = embedded::capitalize(inputs, &mut outputs);
    tokio::task::LocalSet::new()
        .run_until(flow.run_available())
        .await;
    drop(flow);

    assert_eq!(results, vec!["HELLO", "WORLD"]);
}
```

The generated function accepts an `EmbeddedInputs` struct, with one named field per input (each stream input is any `Stream<Item = T> + Unpin`), and a mutable reference to the `EmbeddedOutputs` struct, with one named `FnMut` closure per output, wrapped in an `OutputChannel` (see [Requiring Guarantees from Outputs](#requiring-guarantees-from-outputs)). It returns a [`Dfir`](rust:dfir_rs::scheduled::context::Dfir) graph that you run with [`run_available()`](rust:dfir_rs::scheduled::context::Dfir::run_available) (or tick manually).


## Singleton Inputs

In addition to stream inputs, you can pass singleton values into embedded mode. A **singleton input** becomes a plain `T` field of `EmbeddedInputs` — no stream wrapping needed. This is useful for configuration values, thresholds, or any fixed data that the dataflow needs.

Use [`Location::embedded_singleton_input`](rust:hydro_lang::location::Location::embedded_singleton_input) instead of `embedded_input`:

```rust title="my_hydro_crate/src/lib.rs"
use hydro_lang::prelude::*;

pub fn greet<'a>(
    names: Stream<String, Process<'a, ()>, Unbounded, TotalOrder, ExactlyOnce>,
    greeting: Singleton<String, Process<'a, ()>, Bounded>,
) {
    names
        .cross_singleton(greeting)
        .map(q!(|(name, greeting)| format!("{greeting}, {name}!")))
        .embedded_output("output");
}
```

In `build.rs`, call `embedded_singleton_input` to create the singleton parameter:

```rust title="my_wrapper_crate/build.rs"
let process = flow.process::<()>();
my_hydro_crate::greet(
    process.embedded_input("names"),
    process.embedded_singleton_input("greeting"),
);
```

The generated `EmbeddedInputs` struct holds `greeting` as a plain `String`:

```rust,ignore
pub mod greet {
    pub struct EmbeddedInputs<In0: Stream<Item = String> + Unpin> {
        pub names: InputChannel<inputs::names, In0>,
        pub greeting: String,
    }
}

pub fn greet<'a, In0: Stream<Item = String> + Unpin + 'a, ...>(
    __inputs: greet::EmbeddedInputs<In0>,
    __outputs: &'a mut greet::EmbeddedOutputs<...>,
) -> Dfir<'a> { ... }
```

Call it like any other Rust function:

```rust,ignore
let input = futures::stream::iter(vec!["Alice".to_owned(), "Bob".to_owned()]);
let mut results = vec![];
let mut outputs = embedded::greet::EmbeddedOutputs {
    output: OutputChannel::new(|s: String| results.push(s)),
};
let inputs = embedded::greet::EmbeddedInputs {
    names: InputChannel::new(input, Promises::new().total_order(manual_proof!(/** ... */)).exactly_once(manual_proof!(/** ... */))),
    greeting: "Hello".to_owned(),
};
let mut flow = embedded::greet(inputs, &mut outputs);
```


## Clusters

When a location is a cluster (registered with [`with_cluster`](rust:hydro_lang::compile::builder::FlowBuilder::with_cluster) in `build.rs`), the generated function receives additional parameters for the cluster's identity and membership information.

### Self ID
A function generated for a cluster location receives a `__cluster_self_id` parameter of type [`&TaglessMemberId`](rust:hydro_lang::location::member_id::TaglessMemberId). This tells the running instance which member of the cluster it is. You provide this when you call the generated function:

```rust,ignore
let member_id = TaglessMemberId::from_raw_id(0);
let mut flow = my_cluster_fn(&member_id, my_cluster_fn::EmbeddedInputs { input: InputChannel::new(input, Promises::new().total_order(manual_proof!(/** ... */)).exactly_once(manual_proof!(/** ... */))) }, &mut outputs);
```

### Membership Streams
When a location (process or cluster) needs to know the members of another cluster — for example, to broadcast to it — the generated function receives an `EmbeddedMembershipStreams` struct parameter. This struct has one field per cluster whose membership is needed, named after that cluster's function name. Each field is a stream of ([`TaglessMemberId`](rust:hydro_lang::location::member_id::TaglessMemberId), [`MembershipEvent`](rust:hydro_lang::location::MembershipEvent)) pairs, wrapped in an `InputChannel` like a stream input, since the dataflow processes the events in order and each once (see [Promising Guarantees](#promising-guarantees)):

```rust,ignore
pub mod my_sender {
    pub struct EmbeddedMembershipStreams<S: Stream<Item = (TaglessMemberId, MembershipEvent)> + Unpin> {
        pub my_receiver: InputChannel<membership::my_receiver, S>,
    }
}
```

You provide the membership stream when calling the function. For example, a process that sends to a cluster:

```rust,ignore
use hydro_lang::location::MembershipEvent;
use hydro_lang::location::member_id::TaglessMemberId;

let member_id = TaglessMemberId::from_raw_id(0);
let membership = my_sender::EmbeddedMembershipStreams {
    my_receiver: InputChannel::new(
        futures::stream::iter(vec![(member_id.clone(), MembershipEvent::Joined)]),
        Promises::new()
            .total_order(manual_proof!(/** the events are listed in order */))
            .exactly_once(manual_proof!(/** each event is listed once */)),
    ),
};
let mut flow = my_sender(membership, my_sender::EmbeddedInputs { input: InputChannel::new(input, Promises::new().total_order(manual_proof!(/** ... */)).exactly_once(manual_proof!(/** ... */))) }, &mut net_out);
```

A cluster that sends to another cluster receives both `__cluster_self_id` and the membership struct:

```rust,ignore
let mut flow = m2m_sender(&src_id, membership, m2m_sender::EmbeddedInputs { input: InputChannel::new(input, Promises::new().total_order(manual_proof!(/** ... */)).exactly_once(manual_proof!(/** ... */))) }, &mut net_out);
```

In `build.rs`, use `with_cluster` instead of `with_process` to register cluster locations:

```rust,ignore
let cluster = flow.cluster::<MyClusterTag>();
// ...
let code = flow
    .with_cluster(&cluster, "my_cluster_fn")
    .generate_embedded("my_crate");
```

## Networking

When your Hydro program uses [`.send()`](rust:hydro_lang::live_collections::Stream::send) between locations, the generated functions get extra parameters so you can wire up the transport yourself. By default (with [`.bincode()`](rust:hydro_lang::networking::NetworkingConfig::bincode) serialization), Hydro automatically handles serialization — just shuttle the raw bytes between sender and receiver. Alternatively, an [`EMBEDDED` channel](#host-implemented-channels-embedded) exposes the raw element type instead of bytes, so you implement (and, if you need to, serialize) the channel however you like. In either case, you must ensure that you are preserving any guarantees of the network config specified in the Hydro program. For example, if the channel uses `TCP.fail_stop()` or `EMBEDDED.exactly_once().total_order().fail_stop()`, you must ensure that your networking mechanism delivers, per sender, an in-order prefix of the messages sent.

Network channels in embedded mode **must be named**. Use [`.name()`](rust:hydro_lang::networking::NetworkingConfig::name) on the networking config:

```rust,ignore
input.send(receiver, TCP.fail_stop().bincode().name("messages"))
```

The name becomes a field name in the generated structs, so it must be a valid Rust identifier.

### Process-to-Process (o2o)

Consider a two-process program where `Sender` sends to `Receiver` over a channel named `"messages"`. `Sender` gets an `EmbeddedNetworkOut` struct parameter with an `FnMut(Bytes)` field per outgoing channel:

```rust,ignore
pub mod echo_sender {
    pub struct EmbeddedNetworkOut<F: FnMut(Bytes)> {
        pub messages: OutputChannel<outgoing::messages, F>,
    }
}

pub fn echo_sender<'a, In0: Stream<Item = String> + Unpin + 'a, F: FnMut(Bytes) + 'a>(
    __inputs: echo_sender::EmbeddedInputs<In0>,
    __network_out: &'a mut echo_sender::EmbeddedNetworkOut<F>,
) -> Dfir<'a> { ... }
```

On the other side, `Receiver` gets an `EmbeddedNetworkIn` struct parameter with a `Stream<Item = Result<BytesMut, io::Error>>` field per incoming channel:

```rust,ignore
pub mod echo_receiver {
    pub struct EmbeddedNetworkIn<S: Stream<Item = Result<BytesMut, io::Error>> + Unpin> {
        pub messages: InputChannel<incoming::messages, S>,
    }
}

pub fn echo_receiver<'a, S: Stream<Item = Result<BytesMut, io::Error>> + Unpin + 'a>(
    __outputs: &'a mut echo_receiver::EmbeddedOutputs<...>,
    __network_in: echo_receiver::EmbeddedNetworkIn<S>,
) -> Dfir<'a> { ... }
```

### Cluster Networking

When a cluster is involved in networking, the generated structs become **tagged** with `TaglessMemberId` so you can route messages to and from individual cluster members.

#### Process → Cluster (o2m)

When a process sends to a cluster, the sender's `EmbeddedNetworkOut` fields become `FnMut((TaglessMemberId, Bytes))` — each outgoing message is paired with the target member ID:

```rust,ignore
pub mod o2m_sender {
    pub struct EmbeddedNetworkOut<F: FnMut((TaglessMemberId, Bytes))> {
        pub data: OutputChannel<outgoing::data, F>,
    }
}
```

The receiving cluster's `EmbeddedNetworkIn` fields use untagged `Stream<Item = Result<BytesMut, io::Error>>` since each cluster member only receives its own messages:

```rust,ignore
pub mod o2m_receiver {
    pub struct EmbeddedNetworkIn<S: Stream<Item = Result<BytesMut, io::Error>> + Unpin> {
        pub data: InputChannel<incoming::data, S>,
    }
}
```

Your transport layer is responsible for routing: when the sender calls the `FnMut` with `(member_id, bytes)`, you deliver `bytes` to the instance running with that `__cluster_self_id`.

#### Cluster → Process (m2o)

When a cluster sends to a process, the sender's `EmbeddedNetworkOut` fields are untagged `FnMut(Bytes)` since each cluster member just sends its own data:

```rust,ignore
pub mod m2o_sender {
    pub struct EmbeddedNetworkOut<F: FnMut(Bytes)> {
        pub data: OutputChannel<outgoing::data, F>,
    }
}
```

The receiving process's `EmbeddedNetworkIn` fields become `Stream<Item = Result<(TaglessMemberId, BytesMut), io::Error>>` — each incoming message is tagged with the sender's member ID:

```rust,ignore
pub mod m2o_receiver {
    pub struct EmbeddedNetworkIn<S: Stream<Item = Result<(TaglessMemberId, BytesMut), io::Error>> + Unpin> {
        pub data: InputChannel<incoming::data, S>,
    }
}
```

Your transport layer must tag each incoming message with the `TaglessMemberId` of the cluster member that sent it.

#### Cluster → Cluster (m2m)

When a cluster sends to another cluster, both sides are tagged. The sender's `EmbeddedNetworkOut` fields are `FnMut((TaglessMemberId, Bytes))` (tagged with the target member ID):

```rust,ignore
pub mod m2m_sender {
    pub struct EmbeddedNetworkOut<F: FnMut((TaglessMemberId, Bytes))> {
        pub data: OutputChannel<outgoing::data, F>,
    }
}
```

The receiver's `EmbeddedNetworkIn` fields are `Stream<Item = Result<(TaglessMemberId, BytesMut), io::Error>>` (tagged with the source member ID):

```rust,ignore
pub mod m2m_receiver {
    pub struct EmbeddedNetworkIn<S: Stream<Item = Result<(TaglessMemberId, BytesMut), io::Error>> + Unpin> {
        pub data: InputChannel<incoming::data, S>,
    }
}
```

Your transport layer must handle both directions: route outgoing `(target_id, bytes)` to the correct destination member, and tag incoming messages with the `source_id` of the sender.

### Channel Marker Types

Each location's generated module has a zero-sized **marker type** for each channel crossing the location's boundary, named exactly like the field it describes: under `incoming::*` and `outgoing::*` for network channel ends (a channel named `"messages"` is `echo_receiver::incoming::messages` at its receiver and `echo_sender::outgoing::messages` at its sender), and under `inputs::*`, `membership::*`, and `outputs::*` for the location's stream inputs, membership streams, and outputs. Every marker implements [`EmbeddedChannel`](rust:hydro_lang::compile::embedded_runtime::EmbeddedChannel), which carries the guarantees of its channel (`Boundedness`, `Ordering`, and `Retries`, see [Promising Guarantees](#promising-guarantees)).

Each field's type is a wrapper over its marker type: an [`InputChannel<Marker, _>`](rust:hydro_lang::compile::embedded_runtime::InputChannel) for everything flowing into the dataflow, for example `data: InputChannel<incoming::data, S>`, and an [`OutputChannel<Marker, _>`](rust:hydro_lang::compile::embedded_runtime::OutputChannel) for everything flowing out of it, for example `data: OutputChannel<outgoing::data, F>`. The marker is inferred from the field the wrapper fills, so you never name it.

### Promising Guarantees

Everything flowing into the dataflow — a stream input, a membership stream, or the receiving end of a network channel — comes with guarantees the dataflow relies on, and only the host can provide them. So the generated structs do not take plain streams. Each is an [`InputChannel<Marker, S>`](rust:hydro_lang::compile::embedded_runtime::InputChannel), whose marker type carries the guarantees it must keep (`Boundedness`, `Ordering`, and `Retries`, in the same vocabulary as Hydro's live collections). An `InputChannel` is built from your stream or sink and the [`Promises`](rust:hydro_lang::compile::embedded_runtime::Promises) you make about it, each guarantee **promised separately**, with its own [`manual_proof!`](rust:hydro_lang::prelude::manual_proof) saying why your transport keeps it:

```rust,ignore
use hydro_lang::compile::embedded_runtime::{InputChannel, Promises};
use hydro_lang::prelude::manual_proof;

let net_in = m2m_receiver::EmbeddedNetworkIn {
    m2m_data: InputChannel::new(
        my_stream,
        Promises::new()
            .total_order(manual_proof!(/** one TCP connection per sender, read in order */))
            .exactly_once(manual_proof!(/** nothing is ever resent */)),
    ),
};
```

Nothing stops a host from promising something its transport does not do, but the types make every host write down what it is promising, at the place it wires the channel. `InputChannel::new` accepts any promises that meet the marker's contract, so promising more than a channel needs is fine. Promising less is a compile error at that call, the same one Hydro reports when a stream lacks a guarantee an operator needs, with a note naming the promise to add:

```text
error[E0277]: the stream must be totally ordered (`TotalOrder`), but has order `NoOrder`
  --> src/main.rs:94:13
   |
   = help: the trait `WeakerOrderingThan<NoOrder>` is not implemented for `TotalOrder`
   = note: strengthen the order upstream, or consider a different API
   = note: for an embedded input, the host promises it with `Promises::new().total_order(manual_proof!(/** why the order is kept */))`
```

| Declared | Contract | Promises |
|---|---|---|
| `TCP.fail_stop()`, `TCP.lossy()`, `EMBEDDED.fail_stop()`, `EMBEDDED.lossy()` | `TotalOrder` | `total_order`: per sender, in the order it sent them |
| `TCP.lossy_delayed_forever()`, `EMBEDDED.lossy_delayed_forever()`, `UDP.lossy_delayed_forever()`, `UDP.lossy()` | `NoOrder` | none: any order |
| an `ExactlyOnce` stream sent on any channel | `ExactlyOnce` | `exactly_once`: the transport never delivers a message twice |
| an `AtLeastOnce` stream sent on any channel | `AtLeastOnce` | none: duplicates are allowed |
| `embedded_input::<T, Bounded, _, _>` | `Bounded` | `bounded`: the stream is complete from the start, every element available at once |
| `embedded_input::<T, _, TotalOrder, _>` | `TotalOrder` | `total_order`: the stream's order is the order to process |
| `embedded_input::<T, _, _, ExactlyOnce>` | `ExactlyOnce` | `exactly_once`: every element is a distinct event, delivered once |
| `embedded_input::<T, Unbounded, NoOrder, AtLeastOnce>` | `Unbounded`, `NoOrder`, `AtLeastOnce` | none: `Promises::new()` alone |
| membership of a cluster | `TotalOrder`, `ExactlyOnce` | `total_order` + `exactly_once`: each member's events in the order they happened, each once |

Declare only what the dataflow relies on. An input whose order the dataflow does not use should be `embedded_input::<T, _, NoOrder, _>`, not a `TotalOrder` input weakened right away: the declaration, not later use, is what the host must promise.

The three kinds of promise are independent: boundedness says the whole stream is available at once, ordering says each sender's messages arrive in the order sent, and exactly-once says no message arrives twice. A network channel's ordering comes from the declared transport. Retries come from the stream the dataflow sends, which the network passes on unchanged: an `ExactlyOnce` stream is still `ExactlyOnce` at the receiver, so the transport must not duplicate its messages, while a stream that is already `AtLeastOnce` tolerates duplicates.

A network channel's guarantees are promised once, at its receiving end, where the dataflow relies on them, and the promises cover your whole transport, sending side included. Its sending end flows out of the dataflow, like an output (see [Requiring Guarantees from Outputs](#requiring-guarantees-from-outputs)): an `OutputChannel` over the `outgoing` marker, whose guarantees are what the dataflow sends.

The generated docs of every field and marker also state its contract in words, and list the promises it needs. A reusable transport can build the `InputChannel` itself, generic over the marker (`fn source<C: SatisfiedBy<Unbounded, TotalOrder, ExactlyOnce>>() -> InputChannel<C, _>`), so its promises are written once, next to the code that keeps them, and its [`SatisfiedBy`](rust:hydro_lang::compile::embedded_runtime::SatisfiedBy) bound says which channels it can serve. `SatisfiedBy` checks each guarantee with Hydro's own relations between them, [`WeakerBoundednessThan`](rust:hydro_lang::live_collections::boundedness::WeakerBoundednessThan), [`WeakerOrderingThan`](rust:hydro_lang::live_collections::stream::WeakerOrderingThan), and [`WeakerRetryThan`](rust:hydro_lang::live_collections::stream::WeakerRetryThan), the same ones that bound `weaken_boundedness`, `weaken_ordering`, and `weaken_retries` on a stream.

Network channels and membership streams are always `Unbounded`, which claims only that elements may keep arriving, so any stream meets it. A stream input is `Bounded` only if the dataflow declares it so, for example to aggregate it and observe the result. Being finite is not enough: a `Bounded` stream must be complete from the start, as Hydro's [bounded collections](../correctness/bounded-unbounded.md) are, so a host promises it only for a stream whose every element is available at once, such as `futures::stream::iter` over a `Vec`. A singleton input is a plain value.

### Requiring Guarantees from Outputs

Outputs run the other way: the dataflow provides the guarantees, and the host's sink may depend on them. Each output field, and each sending end of a network channel, is an [`OutputChannel<Marker, S>`](rust:hydro_lang::compile::embedded_runtime::OutputChannel) over a marker under `outputs` (or `outgoing`), whose [`EmbeddedChannel`](rust:hydro_lang::compile::embedded_runtime::EmbeddedChannel) guarantees are what the dataflow's output stream provides. `OutputChannel::new` requires nothing, so it fits any output. A sink that does depend on a guarantee says so with `.require_bounded()`, `.require_total_order()`, or `.require_exactly_once()`, and the call compiles only if the marker provides it:

```rust,ignore
use hydro_lang::compile::embedded_runtime::OutputChannel;

let mut outputs = my_process::EmbeddedOutputs {
    // Correlates each response by its ID, so it needs no guarantees.
    responses: OutputChannel::new(my_responses_sink),
    // Appends to a log, so it needs order and no duplicates.
    log: OutputChannel::new(my_log_sink).require_total_order().require_exactly_once(),
};
```

`embedded_output` accepts a stream of any boundedness, ordering, and retries, so the dataflow never needs `assume_ordering` just to emit an output. Each requirement is the bound an operator needing that guarantee puts on its input (`IsBounded`, `IsOrdered`, or `IsExactlyOnce`), so requiring what the dataflow does not provide is the same compile error, on the field:

```text
error[E0277]: the input stream must be totally ordered (`TotalOrder`), but has order `NoOrder`
  --> src/main.rs:10:17
   |
   = help: the trait `IsOrdered` is not implemented for `NoOrder`
   = note: strengthen the order upstream, or consider a different API
```

The generated docs of every output field state what the dataflow provides.

### Host-Implemented Channels (`EMBEDDED`)

By default, network channels use [`.bincode()`](rust:hydro_lang::networking::NetworkingConfig::bincode) serialization: Hydro serializes each element to `Bytes` before handing it to your transport, and deserializes the `BytesMut` your transport delivers on the other side. If you want to control how messages travel yourself — for example to use a zero-copy encoding, integrate with an existing protocol, hand off to a transport that carries typed messages, or connect two locations with an in-memory queue — declare the channel [`EMBEDDED`](../locations/network-configuration.md#embedded) instead, naming only the guarantees it must keep:

```rust,ignore
input.send(receiver, EMBEDDED.exactly_once().total_order().fail_stop().name("messages"))
```

An `EMBEDDED` channel is unserialized, so the generated network parameters expose the **raw element type** `T` instead of bytes:

- The sender's `EmbeddedNetworkOut` field becomes `FnMut(T)` (or `FnMut((TaglessMemberId, T))` when tagged with a destination member).
- The receiver's `EmbeddedNetworkIn` field becomes `Stream<Item = T>` (or `Stream<Item = (TaglessMemberId, T)>` when tagged with a source member).

Note that unlike bincode channels, there is **no transport `Result` wrapper** on the receiving side: since your external code performs serialization and transport, it decides how to handle serialization and delivery faults before feeding elements into the stream.

:::tip

If you want to surface transport or deserialization faults *inside* the dataflow, you can make faults part of the element type itself: declare the channel's element type as `Result<T, E>`, send `Ok(...)` values from the Hydro program, and have your transport inject `Err(...)` elements on the receiving side. The element type is symmetric — the same `Result<T, E>` flows out of the sender and into the receiver — which is also what allows the Hydro simulator to pass elements through its in-memory channels unchanged.

:::

For example, the `echo_sender` / `echo_receiver` pair from the [o2o example above](#process-to-process-o2o) would instead be generated as:

```rust,no_run
# fn main() {}
pub mod echo_sender {
    # use hydro_lang::compile::embedded_runtime::OutputChannel;
    # pub mod outgoing { pub struct Messages; }
    pub struct EmbeddedNetworkOut<F: FnMut(String)> {
        pub messages: OutputChannel<outgoing::messages, F>,
    }
}

pub mod echo_receiver {
    # use dfir_rs::futures::Stream;
    # use hydro_lang::compile::embedded_runtime::InputChannel;
    # pub mod incoming { pub struct Messages; }
    pub struct EmbeddedNetworkIn<S: Stream<Item = String> + Unpin> {
        pub messages: InputChannel<incoming::messages, S>,
    }
}
```

An `EMBEDDED` channel declares its retries, ordering, and failure policy; see [Network Configuration](../locations/network-configuration.md#embedded) for what each requires of your channel.

:::note

`EMBEDDED` is only supported in embedded mode and the Hydro simulator; other deployment backends (Hydro Deploy, Maelstrom) will panic at compile time, since Hydro manages the transport there and must serialize the data itself.

:::
